# 배치 크기 산정 — 스케줄러가 0.1초마다 몇 명을 입장시킬까

> **이 문서는 예측값입니다.** 이론으로 "초기값"만 잡고, **Stage 7에서 K6 부하로 실측한 뒤 최종 확정**합니다.
> 이번 주 내내 스스로에게 묻는 질문 하나 — *"우리 DB가 감당할 수 있는 속도로만 주문을 받고 있나?"*

---

## 0. 한 줄 요약

DB 커넥션 풀(40)을 1차 기준으로 **Little's Law**를 두 번 적용해 배치 크기를 정한다.
- **① 배치 산정**: 풀 40 × 안전계수 0.7 ÷ 점유시간 0.2s = **초당 140건 → 0.1초당 14명**
- **② 쌓임 검증**: 발급 140/s × 토큰 수명 300s = **동시에 42,000명이 "주문 가능" 상태로 무장** → 순간 폭주 위험 확인
- 이 값들은 **가정 위에 세운 예측**이며 Stage 7 실측으로 조정한다.

---

## 1. 전제와 확인된 사실

배치 크기를 감으로 정하지 않으려면, 먼저 "무엇이 진짜 병목인가"를 코드로 확인해야 한다.

| 항목 | 값 / 사실 | 출처 |
|---|---|---|
| DB 커넥션 풀 크기 | **40** | `modules/jpa/src/main/resources/jpa.yml` `maximum-pool-size: 40` |
| 커넥션 획득 대기 | 3초 (초과 시 예외) | 같은 파일 `connection-timeout: 3000` |
| 주문 트랜잭션 내용 | **DB 작업만** (재고 `FOR UPDATE` + 주문 `INSERT`) | `OrderFacade.createOrder` |
| 결제(PG 외부 호출) 위치 | **주문 트랜잭션 밖** — 별도 API `POST /payments` | `PaymentFacade.createPayment` |
| 앱 인스턴스 수 | **1대 전제** (여러 대는 한계로만 기록) | 이번 과제 범위 |

**핵심 확인**: 대기열이 지키는 문은 `POST /orders` 한 곳이고, 그 트랜잭션은 **순수 DB 작업**이다. 느린 PG 호출은 대기열 밖의 별도 API(`POST /payments`)에 있으므로 **커넥션 점유시간에 포함되지 않는다.** 덕분에 점유시간이 짧다는 가정이 성립한다.

---

## 2. 왜 커넥션 풀이 1차 기준인가 (톰캣 스레드는?)

```
                        ┌─ 톰캣 스레드(≤200) ─┐
  요청 ──▶ 주문 API ──▶ │  요청당 1개 점유    │ ──▶ DB 커넥션 풀(40) ──▶ MySQL(CPU/락)
                        └──────────────────┘         │ 주문당 1개 점유
                                                      └─ 트랜잭션 = DB만(PG 없음)
```

- **커넥션 풀은 가장 늘리기 어려운 자원**이다. API 서버(=톰캣 스레드)는 쉽게 늘려도, DB는 못 늘린다. 대기열은 바로 이 DB를 지키려고 있다.
- **톰캣 스레드 고갈은 원인이 아니라 증상**이다. 스레드가 묶이는 건 *커넥션을 못 얻어 대기하기 때문*. 그래서 "풀이 절대 초과 예약되지 않는 속도"로 흘려보내면, 스레드가 커넥션을 기다리며 쌓일 일 자체가 없어져 스레드 고갈 연쇄가 발생하지 않는다. **풀 기준으로 조이면 스레드는 구조적으로 함께 지켜진다.**
- 우리 목표치(~140/s × 짧은 점유)면 동시 처리 요청은 수십 개로, 200 스레드 근처도 가지 않는다.

---

## 3. ① 배치 산정 — 커넥션 풀 = 시스템

Little's Law `L = λ × W`를 **λ(허용 처리율)에 대해 푼다.** 사실 "풀 ÷ 점유시간"이라는 계산이 곧 Little's Law이다.

```
시스템    = DB 커넥션 풀
L(안엣것) = 동시에 커넥션 잡고 처리 중인 주문 수  ≤  안전 용량
W(머묾)   = 커넥션 점유시간 = 0.2초  (가정값 — Stage 7 실측 대상)
λ(도착)   = 우리가 허용할 주문 처리율  ← 구하려는 값

안전 용량 = 40 × 0.7 = 28           (안전계수 0.7 = DB에 30% 여유)
L = λ × W  →  28 = λ × 0.2  →  λ = 140건/초
배치 크기 = 140 ÷ 10 = 14명          (스케줄러가 0.1초마다 도니까 ÷10)
```

**→ 초기 배치 크기 = 0.1초당 14명 (초당 140건 발급)**

> 안전계수 0.7의 의미: DB CPU·락 경합 등 이 계산이 모델링하지 못한 변수를 위한 여유 버퍼. 100%를 쓰지 않는다.

---

## 4. ② 쌓임 검증 — 살아있는 입장권 = 시스템

①은 "주문이 140/s로 *도착하면* 풀이 버틴다"만 보장한다. **"동시에 몇 명이 주문할 자격을 갖고 있나"는 보지 않는다.** 입장권은 5분을 살아있어 계속 쌓이기 때문에, 같은 Little's Law를 **다른 대상**에 다시 적용한다.

```
시스템    = "유효한 입장권을 든 사람" (발급됐고 아직 안 쓰고 안 만료됨)
L(안엣것) = 지금 이 순간 언제든 주문 가능한 사람 수  ← 구하려는 값
λ(도착)   = 토큰 발급률 = 140/초  (①의 배치 속도)
W(머묾)   = 토큰 수명 = TTL = 300초(5분)

L = λ × W = 140 × 300 = 42,000명
```

**파티 방 비유**: 1초에 140명을 들여보내는데 각자 5분 머물면, 어느 순간 방 안엔 42,000명이 있다. 이 42,000명은 모두 "지금 당장 주문 가능"하다. 이들이 한꺼번에 `POST /orders`를 치면, 140/s만 버티게 설계한 풀이 **순간 폭주로 뚫린다.** ①의 안전한 *평균* 속도가 *순간* 동시성을 막지 못하는 것이다.

### 조정 knob (넘치면 무엇을 조이나)

| knob | 효과 | 대가 |
|---|---|---|
| 발급률 ↓ (배치 ↓) | 무장 인원 L 감소 | 대기 시간이 길어짐 |
| **TTL ↓** | L 급감 (예: 60초 → `140×60 = 8,400`) | 결제 늑장 부리면 만료 → 재입장(UX 저하) |

### 현실 보정

실제로는 42,000명이 *동시에* 쏘지 않는다 — 사람은 5분에 걸쳐 흩어져 결제하고, 대기열이 그만큼 깊을 때만 쌓인다. 또 커넥션 획득 대기(3초)를 넘긴 초과분은 예외로 거절되어(대기열 back-pressure) DB가 무너지는 대신 재시도로 흡수된다. **그래도 "무장 토큰이 이만큼 쌓인다"는 사실 자체가 위험 신호**이므로, Stage 7에서 실제 폭주가 일어나는지 측정하고 필요하면 배치·TTL을 조인다.

## 7. Stage 7에서 검증·조정할 것

- [ ] **점유시간 실측** — 경합 없는 0.2초 가정이 맞나. `FOR UPDATE` 핫로우 경합 시 실효 점유시간이 얼마나 커지나
- [ ] **실제 처리 상한** — 배치 14명일 때 DB CPU·락 대기·에러율이 안전 구간인가
- [ ] **쌓임 실측** — 무장 토큰이 실제로 순간 폭주로 이어지나, 아니면 자연 분산되나
- [ ] **재조정 기록** — 계산(14명)과 실측이 다르면, 이유와 함께 최종 배치·TTL을 이 문서에 갱신
