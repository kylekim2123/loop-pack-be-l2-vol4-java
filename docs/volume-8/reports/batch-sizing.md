# 배치 크기 산정 — 스케줄러가 0.1초마다 몇 명을 입장시킬까

> **이 문서는 예측값입니다.** 이론으로 "초기값"만 잡고, **Stage 7에서 K6 부하로 실측한 뒤 최종 확정**합니다.
> 이번 주 내내 스스로에게 묻는 질문 하나 — *"우리 DB가 감당할 수 있는 속도로만 주문을 받고 있나?"*

---

## 0. 한 줄 요약

DB 커넥션 풀(40)을 1차 기준으로 **Little's Law**를 두 번 적용해 배치 크기를 정한다.
- **① 배치 산정**: 풀 40 × 안전계수 0.7 ÷ 점유시간 0.2s = **초당 140건 → 0.1초당 14명**
- **② 쌓임 검증**: 발급 140/s × 토큰 수명 300s = **동시에 42,000명이 "주문 가능" 상태로 무장** → 순간 폭주 위험 확인
- 이 값들은 **가정 위에 세운 예측**이며 Stage 7 실측으로 조정한다.

---

## 1. 전제와 확인된 사실

배치 크기를 감으로 정하지 않으려면, 먼저 "무엇이 진짜 병목인가"를 코드로 확인해야 한다.

| 항목 | 값 / 사실 | 출처 |
|---|---|---|
| DB 커넥션 풀 크기 | **40** | `modules/jpa/src/main/resources/jpa.yml` `maximum-pool-size: 40` |
| 커넥션 획득 대기 | 3초 (초과 시 예외) | 같은 파일 `connection-timeout: 3000` |
| 주문 트랜잭션 내용 | **DB 작업만** (재고 `FOR UPDATE` + 주문 `INSERT`) | `OrderFacade.createOrder` |
| 결제(PG 외부 호출) 위치 | **주문 트랜잭션 밖** — 별도 API `POST /payments` | `PaymentFacade.createPayment` |
| 앱 인스턴스 수 | **1대 전제** (여러 대는 한계로만 기록) | 이번 과제 범위 |

**핵심 확인**: 대기열이 지키는 문은 `POST /orders` 한 곳이고, 그 트랜잭션은 **순수 DB 작업**이다. 느린 PG 호출은 대기열 밖의 별도 API(`POST /payments`)에 있으므로 **커넥션 점유시간에 포함되지 않는다.** 덕분에 점유시간이 짧다는 가정이 성립한다.

## 2. 왜 커넥션 풀이 1차 기준인가 (톰캣 스레드는?)

```
                        ┌─ 톰캣 스레드(≤200) ─┐
  요청 ──▶ 주문 API ──▶ │  요청당 1개 점유    │ ──▶ DB 커넥션 풀(40) ──▶ MySQL(CPU/락)
                        └──────────────────┘         │ 주문당 1개 점유
                                                      └─ 트랜잭션 = DB만(PG 없음)
```

- **커넥션 풀은 가장 늘리기 어려운 자원**이다. API 서버(=톰캣 스레드)는 쉽게 늘려도, DB는 못 늘린다. 대기열은 바로 이 DB를 지키려고 있다.
- **톰캣 스레드 고갈은 원인이 아니라 증상**이다. 스레드가 묶이는 건 *커넥션을 못 얻어 대기하기 때문*. 그래서 "풀이 절대 초과 예약되지 않는 속도"로 흘려보내면, 스레드가 커넥션을 기다리며 쌓일 일 자체가 없어져 스레드 고갈 연쇄가 발생하지 않는다. **풀 기준으로 조이면 스레드는 구조적으로 함께 지켜진다.**
- 우리 목표치(~140/s × 짧은 점유)면 동시 처리 요청은 수십 개로, 200 스레드 근처도 가지 않는다.

---

## 3. ① 배치 산정 — 커넥션 풀 = 시스템

Little's Law `L = λ × W`를 **λ(허용 처리율)에 대해 푼다.** 사실 "풀 ÷ 점유시간"이라는 계산이 곧 Little's Law이다.

```
시스템    = DB 커넥션 풀
L(안엣것) = 동시에 커넥션 잡고 처리 중인 주문 수  ≤  안전 용량
W(머묾)   = 커넥션 점유시간 = 0.2초  (가정값 — Stage 7 실측 대상)
λ(도착)   = 우리가 허용할 주문 처리율  ← 구하려는 값

안전 용량 = 40 × 0.7 = 28           (안전계수 0.7 = DB에 30% 여유)
L = λ × W  →  28 = λ × 0.2  →  λ = 140건/초
배치 크기 = 140 ÷ 10 = 14명          (스케줄러가 0.1초마다 도니까 ÷10)
```

**→ 초기 배치 크기 = 0.1초당 14명 (초당 140건 발급)**

> 안전계수 0.7의 의미: DB CPU·락 경합 등 이 계산이 모델링하지 못한 변수를 위한 여유 버퍼. 100%를 쓰지 않는다.

---

## 4. ② 쌓임 검증 — 살아있는 입장권 = 시스템

①은 "주문이 140/s로 *도착하면* 풀이 버틴다"만 보장한다. **"동시에 몇 명이 주문할 자격을 갖고 있나"는 보지 않는다.** 입장권은 5분을 살아있어 계속 쌓이기 때문에, 같은 Little's Law를 **다른 대상**에 다시 적용한다.

```
시스템    = "유효한 입장권을 든 사람" (발급됐고 아직 안 쓰고 안 만료됨)
L(안엣것) = 지금 이 순간 언제든 주문 가능한 사람 수  ← 구하려는 값
λ(도착)   = 토큰 발급률 = 140/초  (①의 배치 속도)
W(머묾)   = 토큰 수명 = TTL = 300초(5분)

L = λ × W = 140 × 300 = 42,000명
```

**파티 방 비유**: 1초에 140명을 들여보내는데 각자 5분 머물면, 어느 순간 방 안엔 42,000명이 있다. 이 42,000명은 모두 "지금 당장 주문 가능"하다. 이들이 한꺼번에 `POST /orders`를 치면, 140/s만 버티게 설계한 풀이 **순간 폭주로 뚫린다.** ①의 안전한 *평균* 속도가 *순간* 동시성을 막지 못하는 것이다.

### 조정 knob (넘치면 무엇을 조이나)

| knob | 효과 | 대가 |
|---|---|---|
| 발급률 ↓ (배치 ↓) | 무장 인원 L 감소 | 대기 시간이 길어짐 |
| **TTL ↓** | L 급감 (예: 60초 → `140×60 = 8,400`) | 결제 늑장 부리면 만료 → 재입장(UX 저하) |

### 현실 보정

실제로는 42,000명이 *동시에* 쏘지 않는다 — 사람은 5분에 걸쳐 흩어져 결제하고, 대기열이 그만큼 깊을 때만 쌓인다. 또 커넥션 획득 대기(3초)를 넘긴 초과분은 예외로 거절되어(대기열 back-pressure) DB가 무너지는 대신 재시도로 흡수된다. **그래도 "무장 토큰이 이만큼 쌓인다"는 사실 자체가 위험 신호**이므로, Stage 7에서 실제 폭주가 일어나는지 측정하고 필요하면 배치·TTL을 조인다.

## 8. Stage 7 실측 결과 (K6, 2026-07-09)

### 측정 방법

- **시나리오**: `measurement/k6/queue-order-flow.js` — 유저 300명(VU)이 **동시에** 대기열 진입 → 1초 간격 순번 폴링 → 입장권 수령 → 주문까지 관통. 유저·상품은 `seed.sh`, 서버 지표는 `collect-metrics.sh`(0.5초 간격: Redis 대기 인원, Hikari active/pending, CPU)로 수집. 원자료는 `reports/data/`.
- **환경**: 랩톱(Apple Silicon) 1대 = 앱 + MySQL·Redis 컨테이너 + K6. **모든 요청이 BCrypt 인증(~수십 ms CPU)을 거치는** 이 프로젝트 고유의 조건이 결과 해석의 핵심 변수였다.

### 회차별 결과

| 회차 | 배치(발급/s) | 상품 | 진입 성공 | 주문 성공 | HTTP 실패 | Hikari pending 피크 | 비고 |
|---|---|---|---|---|---|---|---|
| A | 14 (140/s) | 10개 분산 | 278/300 | 278/278 | 22 | 31 | 진입-발급 레이스 발견 |
| A2 | 14 (140/s) | 10개 분산 | 296/300 | 290/296 | 10 | 103 | 레이스 수정 검증 + 진입 응답 NPE 발견, 주문 6건 커넥션 타임아웃 |
| B | 7 (70/s) | 10개 분산 | 300/300 | 270/300 | 33 | **151** | 발급을 늦췄는데 **악화** — 원인 분석이 전환점 |
| C | **3 (30/s)** | 10개 분산 | **300/300** | **300/300** | **0** | **9** | 안정 — 풀 보호 성공 |
| D | **3 (30/s)** | **1개 핫로우** | **300/300** | **300/300** | **0** | **14** | 최악조건(FOR UPDATE 직렬화)도 안정 |

공통: 진입 파도 동안 system CPU 100% (~7초), Hikari active 피크는 매회 40(풀 전체). 입장권 수령까지 평균 대기 — A2 5.2초 → B 7.7초 → C 20.3초 (배치를 줄인 대가).

### 발견 ① 진입-발급 레이스 (실측이 아니면 못 잡았을 버그)

부하 중 진입 요청 22건이 404("대기열에 진입하지 않았습니다")를 받았다. 원인: 진입 API가 "줄 세우기(ZADD) → 순번 읽기(ZRANK)" 두 단계인데, CPU 포화로 그 사이가 벌어진 틈에 **스케줄러가 그 유저를 꺼내 입장권을 발급**(ZREM). 유저는 입장권을 쥐고 있는데 서버는 "줄에 없다"고 답한 것 — **가장 빨리 처리된 유저가 에러를 받는** 역설. 통합 테스트에선 스케줄러를 수동 호출해서(test 프로파일 `@Scheduled` 비활성) 이 동시 실행 자체가 존재하지 않았다.

**수정**: 줄에 없으면 바로 404 대신 **"입장권이 이미 발급됐나?"를 한 번 더 확인**하고, 발급됐으면 `{position: 0, entryToken}`으로 응답 (`QueueFacade` 폴백, 진입·폴링 공통). 후속으로 진입 응답 DTO가 이 분기를 못 담아 NPE가 난 것(A2)까지 고쳐 B부터 진입 실패 0.

### 발견 ② "발급 속도를 늦추면 안전"이 아니었다 (B의 역설)

배치를 14 → 7로 줄였는데 pending이 31 → 151로 **악화**했다. 원인은 Little's Law의 W(점유시간)가 무너진 것:

```
이론:  L = 140/s × 0.2s = 28  ≤ 풀 40           (점유시간 0.2s 가정)
실측:  CPU 포화로 주문 트랜잭션이 수 초씩 걸림
       L = 70/s × ~2s = 140  ≫ 풀 40  → pending 폭발
```

발급 속도(λ)만 조절했는데 정작 **점유시간(W)이 CPU 포화로 10배 이상 부풀어** 있었다. 게다가 발급이 느려지자 대기가 길어져 폴링 총량(요청당 BCrypt)이 늘어 CPU 부하가 가중되는 되먹임까지. **"몇 명씩 꺼내나"보다 "한 건이 얼마나 오래 붙잡나"가 먼저**라는 게 이 실측의 가장 큰 교훈이다.

### 발견 ③ 진짜 병목은 DB가 아니라 앱 CPU(인증)

매 회차 system CPU가 진입 파도 동안 100%였다. 이 프로젝트는 세션 없이 **모든 요청(진입·폴링·주문)마다 BCrypt 비밀번호 검증**(~수십 ms CPU, 의도적으로 느린 연산)을 수행하므로, 이 랩톱의 처리 천장은 풀 40이 아니라 **인증 ~100건/초**였다. TODO가 예고한 "배치 크기를 커넥션 수뿐 아니라 CPU 여유로도 검증"이 정확히 이 지점 — 배치 3은 주문 파도를 CPU 포화 구간 밖으로 밀어내 점유시간을 정상(W ≈ 수백 ms)으로 되돌린 값이다.

### 발견 ④ 쌓임(무장 토큰)의 실제 모습

이론(4절)은 "5분 TTL 동안 42,000명 무장"을 걱정했지만, 실측에서 순간 폭주의 방아쇠는 쌓인 토큰이 아니라 **폴링 응답의 뭉침**이었다: 서버가 바쁜 동안 폴링 응답이 밀렸다가 한꺼번에 배달되면, 수십 명이 거의 동시에 입장권을 받아 **동시에 주문**한다. 발급을 아무리 고르게 해도 **수령이 뭉치면 소용없다** — 놀이공원 입장권을 1분에 10장씩 나눠줘도, 우편함에 넣어두면 다들 같은 시간에 열어보는 것과 같다.

| **배치 크기** | 14명 / 0.1초 (140/s) | **3명 / 0.1초 (30/s)** | 14·7은 커넥션 풀 붕괴(pending 31~151, 주문 실패), 3은 분산·핫로우 모두 실패 0 + pending ≤ 14 |
| 토큰 TTL | 300초 | **300초 유지** | 폭주 방아쇠가 TTL 쌓임이 아니라 폴링 뭉침으로 실측됨 — TTL을 줄여도 이 문제엔 효과 없음 |
| 스케줄러 주기 | 0.1초 | 0.1초 유지 | 배치 크기로 충분히 조절됨 |

- 확정값은 `application.yml`의 `queue.batch-size: 3`에 반영 (@ConfigurationProperties라 환경 바뀌면 재컴파일 없이 재조정).
- **대가**: 발급 30/s에서 300명 기준 입장권 수령까지 평균 ~20초. DB(와 CPU)를 지키는 값이 유저 대기를 늘리는 전형적 트레이드오프 — 이 순서(시스템 보호 > 대기시간)가 대기열의 존재 이유다.

### 이 확정값의 전제 (환경이 바뀌면 재측정)

1. **요청당 BCrypt 인증이라는 이 프로젝트의 조건**이 지배 변수였다. 세션/토큰 인증으로 바뀌면 CPU 천장이 사라져 이론값(14)에 가까운 배치가 다시 유효할 수 있다 — 그때 이 문서의 루프(이론→실측→재조정)를 다시 돌린다.
2. 랩톱 1대에 앱·DB·부하기가 동거한 측정이라 절대 수치보다 **경향(어느 배치에서 풀이 뚫리고 회복되는가)**이 결론이다.
3. 폴링 뭉침 완화(수령 시점 분산)는 배치 크기 밖의 knob — TODO "안 하는 것"의 폴링 주기 조절·Jitter 확장에 해당한다.
